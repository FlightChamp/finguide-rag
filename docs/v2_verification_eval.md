# FinGuide-RAG v2 — 상담 답변 검증기 평가

> 공개 문서 기반 개인 포트폴리오 프로젝트의 평가 기록입니다. 어떤 금융기관의 공식 서비스나 평가가 아닙니다.

## 요약

| 지표 (held-out v1, 사람 라벨 N 13 · Y 37) | 값 | 95% 신뢰구간 |
|---|---|---|
| 오류 답변 탐지율 (N 중 최종 판정 ≠ 안내 가능) | **9/13 = 0.69** | 0.42–0.87 |
| 정상 답변 '확인 필요' 표시율 (soft 오탐) | 11/37 = 0.30 | 0.17–0.46 |
| 정상 답변 '안내 금지' 오판율 (hard 오탐) | **1/37 = 0.03** | 0.00–0.14 |
| 경고 중 실제 오류 비율 | 9/20 = 0.45 | — |

- 검증기: claim 분해·근거 정렬은 LLM(`gpt-4.1-mini`, 정렬 프롬프트 cv-v1), 판정은 규칙(사유 코드 → 판정).
- **초안 수준 범위 검사(MIXED_SCOPE / SCOPE_MISMATCH)를 추가해도 held-out 판정은 한 건도 바뀌지 않았다(효과 0, 오탐 추가 0).**
- 신뢰구간이 넓다(N=13). 이 수치는 '대략 이 정도'를 말해줄 뿐, 다른 시스템과 정밀 비교할 근거는 아니다.

## 평가 절차 — 숫자를 믿을 수 있게 만든 장치

1. **개발 셋과 held-out 분리.** 규칙과 프롬프트는 v1 답변 73건(정상 초안 30 + 개발 43)과 자연 오류 8건으로만 만들었다. 이 셋은 공식 수치에 쓰지 않는다.
2. **새 held-out 생성.** 개발 셋 답변이 인용한 적 없는 청크에서 v1 방식으로 질문 77개를 만들고, v1 파이프라인으로 답변해 답변된 56건 중 50건을 층화 추출했다. 기존 평가셋 질문과 겹치는 질문은 제외했다.
3. **블라인드 라벨.** 검수 페이지에는 검증기·규칙 정보가 전혀 없고 순서는 무작위였다. 라벨: Y(그대로 안내 가능) / N(안 됨, 사유 복수 선택 + 메모) / X(평가 불가).
4. **freeze 후 1회 평가.** 라벨을 확정해 해시를 기록하고 커밋한 뒤(`6ab28cd`, 23:26) 평가를 실행했다(`00641e4`, 23:29). freeze 시점과 평가 시점의 검증 코드 지문이 같다(`473eada7ec10dc1e`). 이후 코드를 바꿔 다시 평가하면 결과는 자동으로 `UNOFFICIAL`로 표시된다.

## 개발 과정에서 기각한 것 (같은 데이터로 고치면 생기는 일)

| 시도 | 개발 셋(튜닝에 쓴 셋) | 처음 보는 셋 | 결정 |
|---|---|---|---|
| 정렬 프롬프트 cv-v2 (조건 정의 강화) | 자연 오류 적중 3/8 → 4/8 | 오류 탐지 8/15 → **3/15**, 정상 오탐 10/28 → 7/28 | **기각.** 결과가 갈린 10건 중 cv-v2가 맞은 4건은 전부 오탐 감소, cv-v1이 맞은 6건 중 5건은 실제 오류 탐지 |
| LLM 추출 슬롯을 '고객정보 필요' 사유로 승격 | 정상 claim 경고 0.57, 자연 오류 '탐지'의 절반이 엉뚱한 코드 | — | **제거.** 정상 claim 경고 0.57 → 0.19, 안내 금지 오판 0.10 → 0.00 |
| 초안 수준 범위 검사 | 표적 4/4, 정상 53건 오탐 0 | 판정 변화 **0건** | 유지하되 효과 없음으로 기록 (아래) |

## 범위 검사가 held-out에서 효과가 없었던 이유

범위 검사는 개발 셋의 한 가지 패턴 — **서로 다른 상품 문서를 근거로 섞거나, 질문에 없는 상품명을 들어 답하는 경우** — 를 겨냥했다. held-out에서 사람이 SCOPE_MISMATCH·MIXED_SCOPE로 분류한 8건은 성격이 달랐다.

- 상품 혼합이 아니라 **질문의 관점과 다른 답변**: "은행이 금을 사는 가격"을 묻는데 고객이 살 때의 가격을 설명(h025), 특정 예시표의 금액을 일반 답처럼 제시(h009)
- 이 중 6건은 claim 단위 검증이 이미 `MISSING_CONDITION` 등으로 잡았고, 범위 검사는 1건(h048)에서만 울렸는데 그 건도 이미 다른 사유로 경고 중이었다.

즉 개발 셋에서 본 오류 패턴이 처음 보는 데이터에서는 다른 모양으로 나타났다. 개발 셋 4/4는 실제 효과를 말해주지 않았다.

## 무엇을 놓치고, 어디서 틀리는가

**놓친 오류 4건 — 전부 '의미' 오류**

| ID | 사유 | 내용 |
|---|---|---|
| h054 | WRONG | 환매채무 이행 주체(채무자)와 할인료 반환 주체(은행)가 뒤바뀜 |
| h025 | SCOPE_MISMATCH · WRONG | 질문 관점(은행이 살 때)과 반대 관점(고객이 살 때)으로 설명 |
| h009 | WRONG · SCOPE_MISMATCH | "4년째 이율"을 묻는데 특정 예시표의 4년차 이자액을 일반화 |
| h033 | OMITTED | 연장 시 금리가 어떤 기준으로 정해지는지에 답하지 않음 |

수치·상품명·기관명 같은 문자열 대조로 잡히는 오류는 없었다. 남은 과제는 **주체·관점·질문 의도**를 보는 검사다. WRONG 5건 중 사유에 맞는 코드(CONTRADICTED 등)로 잡은 것은 0건이다.

**정상 답변 경고 11건 — 주로 과민한 단정·조건 판정**

| 원인 | 건수 (중복 포함) |
|---|---|
| `OVERSTATED` (규칙: 원문 대비 헤지 소실·강조어) | 6 |
| `MISSING_CONDITION` (LLM) | 5 |
| `VERIFIER_ERROR` (LLM 응답 형식 오류 → 안전하게 '확인 필요') | 2 |
| `CONTRADICTED` → 안내 금지 (h074) | 1 |

h074는 사람은 정상으로, 검증기는 근거와 모순으로 판정했다. 라벨이 freeze되어 있어 이 평가에서는 고치지 않는다.

**문서 유형별 v1 답변 오류율 (사람 라벨)**

| 유형 | N / 전체 |
|---|---|
| 약관 | **9 / 15** |
| 설명서 | 4 / 18 |
| FAQ | 0 / 17 |

개발 셋에서도 약관 답변의 오류가 가장 많았다(정상 초안 풀 3/8, 개발 43건 5/8). 두 셋에서 같은 방향이다. 단서 조항이 많은 약관에서는 v1 답변 자체를 더 보수적으로 다뤄야 한다는 근거다.

## 한계

- **표본이 작다.** N=13이라 탐지율 구간 폭이 0.45다.
- **라벨러 1인.** 판정 기준이 한 사람의 해석에 의존한다. 개발 셋 검수와 held-out 검수 사이에 기준이 엄격해졌을 가능성이 있다.
- **같은 모델 계열.** v1 답변 생성과 v2 검증의 LLM이 모두 `gpt-4.1-mini`다. 같은 맹점을 공유할 수 있다.
- **근거 범위 고정.** 검증은 v1 답변이 인용한 근거 청크 안에서만 했다. claim별 보조 검색은 아직 붙이지 않았다.
- **held-out v1은 이제 소진됐다.** 이 결과를 보고 규칙을 고치면, 그 개선은 새 held-out으로만 주장할 수 있다.

## 다음 단계

1. **의미 오류 검사**: 초안 전체가 질문의 주체·관점·의도에 맞게 답했는지 보는 초안 수준 LLM 검사(OMITTED·관점 불일치 대상).
2. **오탐 감소**: `OVERSTATED` 규칙과 LLM `MISSING_CONDITION`의 과민 판정. 개발 셋으로 조정한다.
3. **약관 답변 정책**: 약관 근거 답변에 더 엄격한 기본값(예: 원문 인용 우선 표시).
4. 위 변경의 효과는 **새 held-out v2**로만 측정한다.
